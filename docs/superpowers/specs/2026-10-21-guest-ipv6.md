# Guest IPv6 egress — Design

**Date:** 2026-10-21
**Status:** Draft, implemented on `feature/kiln-ipv6-07b417` (kiln) and `feature/ipv6-egress` (vmkit)
**Amends:** `2026-09-30-kiln-design.md` §1 (non-goals), §3 (T5), §9.3 and §9.6 stage 5

## Problem

Guests get IPv4 only. The VM namespace's forward chain drops every IPv6 packet from the tap (`iifname "tap0" meta nfproto ipv6 drop`), and pasta runs with `--ipv4-only`. A workload that resolves an AAAA-only name, or that prefers IPv6, has no network.

Letting IPv6 through safely needs three things that IPv4 already has, or does not need:

- **A deny list.** IPv6 has its own link-local, private (ULA), loopback, multicast and reserved ranges. It also has prefixes that embed IPv4 addresses (v4-mapped, NAT64, 6to4, Teredo), which could reach the IPv4 ranges T5 denies.
- **Anti-spoofing.** Only the guest's assigned source address may leave the tap.
- **Neighbour discovery.** This is ICMPv6, not a separate protocol like ARP, so it reaches the namespace's input chain. Router advertisements and redirects from the guest must never configure the namespace.

## Where the work lives

The network policy is in **vmkit** (`src/net.rs` for the ruleset, pasta options and host addresses; `src/bin/vmkit-sandbox.rs` `setup_net` for the tap, sysctls and nftables load; `tests/network.rs` and `testguest/` for the hostile-guest suite). kiln owns the guest side: the `Config.network` message (`kiln-proto`), `kiln-init` stage 5 and the boot test. kiln pins vmkit by git revision, so kiln moves its pin to the vmkit branch that carries this change.

## Decisions

### D1. Upstream model: NAT66 behind a fixed ULA, through pasta

The guest gets `fd76:6d6b:6974::2/64` (the global ID is ASCII `vmkit`) with gateway `fd76:6d6b:6974::1` on `tap0`. The namespace masquerades it out of `egress0`, and pasta carries it through host sockets. This is the IPv4 design with a different address family: one address per VM, and every VM in its own namespace, so nothing collides.

The alternatives need privileges kiln does not have. A routed global address per guest would need a delegated prefix and proxy NDP on the host. A bridge onto the host's link would need host network configuration. Neither is unprivileged.

One consequence: under RFC 6724 a ULA source with a global destination gets a lower preference than IPv4. Resolvers that sort addresses (glibc, musl) put IPv4 first when a name has both A and AAAA records, and use IPv6 when there is only an AAAA record. Docker behaves the same way with ULA plus NAT66.

### D2. pasta runs dual-stack for the VM network, when asked and when the host has IPv6

IPv6 is opt-in in vmkit (`NetSpec::ipv6`, off by default; `kiln run --net` sets it), so a vmkit user that never asked for it keeps the IPv4-only namespace, and a root guest there cannot configure the ULA itself and get IPv6 egress. It also needs a host with IPv6 (`/proc/sys/net/ipv6` exists, `vmkit::net::host_has_ipv6`): on a host booted with `ipv6.disable=1`, or a kernel without IPv6, the namespace stays exactly as it was before this change (pasta `--ipv4-only`, IPv6 from the tap dropped, no IPv6 setup in the helper), and kiln sends the guest no IPv6 configuration. A namespace that inherits `disable_ipv6` on the tap skips the tap's IPv6 setup too.

With IPv6, for the tap network (`Network::Tap`), pasta drops `--ipv4-only` and adds `--no-ra --no-dhcpv6`. `--config-net` already writes `egress0`'s addresses and routes, so pasta's own router advertisements and DHCPv6 are not needed. `--no-map-gw` covers IPv6 as well: host loopback stays unreachable.

pasta copies the host's IPv6 address and default route onto `egress0`. On a host with IPv6 but no IPv6 default route, pasta reports "no external interface as template, use local mode", and `egress0` gets only a link-local address and `default via fe80::1`. The guest is still configured, but its IPv6 connections fail when pasta's host socket gets `ENETUNREACH`.

The bare-namespace mode (`Network::Egress`, potter's) is unchanged: it keeps `--ipv4-only` and drops IPv6. It has no guest, and it can follow later with the same sets.

### D3. One `Cidr` type for both families; separate nft sets

`vmkit::net::Cidr` holds an `IpAddr`. `NetSpec.allow` therefore accepts `2001:db8::/32` as well as `10.0.0.0/8`, and every caller gets IPv6 egress options without a second list. A bare address is `/32` or `/128`.

nftables sets have one element type, so the table gets `deny6` and `allow6` (`ipv6_addr`) next to `deny` and `allow`. Each family's rules match their own sets: `ip daddr @allow` and `ip6 daddr @allow6`. `Egress::DenyAll` denies `::/0` as well as `0.0.0.0/0`. `Egress::Open` has no entries in either family.

### D4. The `Restricted` IPv6 deny list

Global unicast is `2000::/3`. The list denies everything outside it, plus the special-purpose ranges inside it:

| Range | Why |
|---|---|
| `::/3` | unspecified `::`, loopback `::1`, IPv4-compatible `::/96`, IPv4-mapped `::ffff:0:0/96` (would reach any IPv4 address), SIIT `::ffff:0:0:0/96`, NAT64 `64:ff9b::/96` and `64:ff9b:1::/48` (embed IPv4), discard `100::/64` |
| `4000::/2` | unallocated, and SRv6 SIDs `5f00::/16` |
| `8000::/1` | ULA `fc00::/7` (IPv6's private ranges; AWS metadata is `fd00:ec2::254`), link-local `fe80::/10` (cloud metadata, the host's link), deprecated site-local `fec0::/10`, multicast `ff00::/8`, and unallocated space |
| `2001::/23` | IETF protocol assignments, including Teredo `2001::/32` (embeds IPv4) and benchmarking `2001:2::/48` |
| `2001:db8::/32`, `3fff::/20` | documentation |
| `2002::/16` | 6to4 (embeds IPv4) |
| the host's connected prefixes | see D5 |

The three covering prefixes are written that way, rather than as a list of named ranges, so that new IANA reservations outside `2000::/3` are denied too. The unit test checks named addresses from every row against the set, including `::1`, `::ffff:10.0.0.1`, `64:ff9b::a9fe:a9fe`, `fd00:ec2::254`, `fe80::1`, `fec0::1`, `ff02::1`, `2001:db8::1`, `2002:a00:1::1` and `3fff::1`, and checks that a public address such as `2606:4700::1111` is not denied.

### D5. The host's own addresses and the networks it reaches directly

IPv4 denies the host's local addresses from `/proc/net/fib_trie`. On IPv4 the host's LANs are almost always RFC 1918 and so are already denied. On IPv6 they are usually global prefixes, so denying addresses alone would let a guest reach the host's LAN neighbours (printers, NAS boxes, other cloud instances in the subnet). The deny set therefore also takes every prefix the host reaches **without a gateway**, from `/proc/net/ipv6_route`: routes with a prefix length above 0, no next hop, and not rejects (`RTF_REJECT`, which the kernel also sets on prefix routes via `lo`). Each is widened to its `/56`, the usual end-site allocation, because the networks a host reaches *through its router* are just as internal: an AWS VPC is a `/56` with one `/64` per subnet, so RDS in a sibling subnet is reached via the default route and would otherwise be allowed, where over IPv4 it would be RFC 1918 and denied. That covers:

- the host's own addresses (local-table `/128` routes);
- its on-link prefixes (LANs, cloud subnets, Docker bridges);
- device routes such as a VPN's prefix;
- each of those widened to its `/56`.

As with IPv4, this is read when the VM is created, and `allow` makes exceptions. Internal networks on global prefixes outside the host's `/56` and reached through a gateway (another VPC peered in, a NAT64 prefix of the operator's) are not known to the host and are not denied: list them with `--egress deny-all` plus `allow=`, or accept them as reachable.

pasta copies the host's outbound IPv6 address onto `egress0`, so the guest can never reach it. `NetSpec::check_allow` refuses an `allow` entry that is exactly that address, as it does for IPv4. `net::outbound_addresses6` finds them as pasta does: the global addresses (`/proc/net/if_inet6`) of the interface on the lowest-metric default route, not by routing a test address, which a more specific route (a VPN's, or `unreachable 2000::/3`) would answer instead.

### D6. Anti-spoofing

Forward: `iifname "tap0" ip6 saddr != fd76:6d6b:6974::2 drop`, before `ct state established,related accept`, beside the existing IPv4 rule. Link-local sources therefore never leave the tap. They could not be routed anyway.

### D7. Neighbour discovery and router advertisements, on the host side

In the namespace (`vmkit-sandbox` `setup_net`):

- `net.ipv6.conf.all.forwarding=1`, in this namespace only, like `ip_forward`. A forwarding interface ignores router advertisements.
- On `tap0`: `accept_ra=0` and `accept_redirects=0` as well, so the namespace never takes a route, address or redirect from the guest even if forwarding were off. Its address is `fd76:6d6b:6974::1/64 nodad`, usable at once.
- **A permanent neighbour entry** for the guest, `fd76:6d6b:6974::2 lladdr 06:00:ac:1e:00:02 nud permanent`. The namespace never learns the guest's link-layer address from the guest. The entry survives the tap's carrier going up and down when the VMM opens and closes it; this was checked on Linux 7.0.
- **Input:** from the tap, only a neighbour solicitation with hop limit 255 and source `fd76:6d6b:6974::2` is accepted. The guest needs that to resolve its gateway. Everything else new is dropped: router solicitations, advertisements, redirects, MLD, echo, and solicitations from any other source, including DAD's `::` and link-local addresses. That last rule bounds the neighbour table for solicitations: the kernel creates an entry for a soliciting source address, and the table's limits are shared by every namespace on the host.
- **A guard at prerouting** (`priority raw`): from the tap, a packet to any other address of the tap's `/64`, or to a link-local address, is dropped unless it is for the gateway. The namespace would route such a packet back out of the tap, and the kernel's redirect for it (sent in `ip6_forward`, before the forward hook) creates a neighbour entry for the destination; without the guard a guest could still fill the shared table, at about one entry a second.
- No router advertisement is ever sent to the guest: the namespace runs no RA daemon, and pasta's are disabled (D2) and only ever on `egress0`. The guest's addressing is whatever `kiln-init` configures.

### D8. Guest configuration over the control channel

`Config.network` gains an optional `ipv6` object: `{ "address", "prefixLen", "gateway" }`.

- **Validation:** `prefixLen` 64–126; the address and gateway are in the same prefix, are different, and are unicast but not link-local, loopback or unspecified; neither is the prefix's all-zeros address (the subnet-router anycast).
- **`kiln-init` stage 5:** after `eth0`'s IPv4 address and route, `kiln-init` adds the IPv6 address with `IFA_F_NODAD` (usable immediately; the namespace drops DAD anyway) and a default route via the gateway, over rtnetlink.
- **Failures:** a kernel without IPv6 fails stage 5 with the kernel's error, as any other `eth0` failure does. kiln's pinned kernels have `CONFIG_IPV6=y`, and a custom kernel is an explicit opt-in.
- **`/etc/hosts`:** the guest's IPv6 address is listed with the hostname after the IPv4 line, as Docker does.
- **DNS:** it stays on the IPv4 gateway (`172.30.0.1`, DNAT'd to pasta's forward address). Answers include AAAA records, so DNS does not need IPv6 transport.

The protocol version does not change. The field is optional, and only a `kiln-init` from the same kiln build receives it. A `kiln-init` built before this change rejects a `Config` that carries `network.ipv6` (`deny_unknown_fields`) when it decodes it, and fails with that message.

### D9. Out of scope

- **IPv6 port forwards.** `PortForward.address` stays `Ipv4Addr`, and forwards still reach `172.30.0.2`.
- **IPv6 for `Network::Egress`.**
- **A global (non-NAT) address for the guest, and DHCPv6 or SLAAC in the guest.**
- **Detecting host IPv6** before boot (D2).
- **The `kiln run` flags.** `--net`, `--egress` and `-p` arrive with M3b-2. Their CIDR options parse into `vmkit::net::Cidr`, so they accept IPv6 without further work.

## Review (2026-10-22)

An adversarial review (security, correctness of each repository, blast radius) found, and this design now fixes:

- **A host without IPv6 could no longer create a tap VM** (the helper's `ip -6` and IPv6 sysctls failed): IPv6 now needs `host_has_ipv6` (D2).
- **Every `Network::Tap` user got IPv6** (another vmkit consumer, sbx, never configures it, and a root guest could): IPv6 is opt-in (D2).
- **Internal networks behind the host's router** (a VPC's other subnets) were allowed: on-link prefixes are widened to `/56` (D5).
- **Redirects created neighbour entries** for any `/64` destination: the prerouting guard (D7).
- **`outbound_address6` missed pasta's copied address** behind a more specific route: it reads the default route's interface (D5).
- **kiln warned that `allow=fe80::/10` reaches link-local**, which never leaves the tap's link: that warning is gone, and an IPv6 exception covering IPv4-mapped addresses (`::ffff:0:0/96`, `::ffff:169.254.169.254`) is warned about instead, since pasta may reach them as IPv4.

## Tests

- **vmkit unit tests (`src/net.rs`):**
  - `Cidr` parsing, normalising and `contains` for both families;
  - the IPv6 deny set covers every D4 row and spares a public address;
  - `DenyAll` and `Open` in both families;
  - rule order: both anti-spoof rules come before `established`, and `allow6` comes before `deny6`;
  - ND input accepts only the guest's solicitations;
  - `ipv6_route` parsing keeps local and connected routes and drops gateway, default and reject routes;
  - `check_allow` for an IPv6 outbound address;
  - pasta options per mode.
- **vmkit sandbox test:** the namespace has `fd76:6d6b:6974::1/64` on `tap0`, IPv6 forwarding on, `accept_ra=0`, and the permanent neighbour entry.
- **vmkit hostile-guest suite (`tests/network.rs`), on both VMMs:**
  - **Fixture:** `testguest/net-fixture.sh` adds `fd00:ec2::254` (metadata), `fd00:250::1` (private) and `3ffe::7` (a host address outside the special ranges) to the host's loopback. When the host has no IPv6 default route, it also adds a dummy template interface (`vmkt6`, `3ffe:0:0:1::1/64`, default route) and `unreachable 2000::/3`. pasta then enables IPv6, and the host's own traffic to the real IPv6 internet fails fast rather than disappearing into the dummy.
  - **Guest:** `testguest/init` gains `vmkit.ip6`, `vmkit.gw6` and IPv6 probes.
  - **Cases:**
    - restricted IPv6 reaches none of metadata, private, host or the gateway;
    - an `allow` exception reaches a private address;
    - a spoofed IPv6 source does not get out;
    - `deny-all` blocks IPv6;
    - `open` reaches the host address.
- **kiln:**
  - `kiln-proto` validation of `network.ipv6`;
  - `kiln-init` netlink messages for `AF_INET6` and `/etc/hosts`;
  - the boot test `networking_from_config`, which checks that the guest has the IPv6 address and default route `kiln-init` configured.
